# Пояснения к презентации защиты

Идёт по слайдам: что на слайде, почему так сделано, что ответить на вопрос. В конце — словарь терминов и сокращений.

---

## 1. MUST PLAY (титул)

Проект отвечает на вопрос «во что поиграть»: берёт открытый датасет Steam, чистит его, считает единый рейтинг всех времён, строит рекомендации и обучает ML-модели. Всё доступно через API на FastAPI и простой веб-интерфейс.

Приоритеты задал преподаватель: **задача минимум — очистка и унификация данных**, вторая задача — **рекомендательная система**, ML — дополнительно.

## 2. Задача и данные

- **141 590 игр загружено** из 141 605 строк файла: 15 строк отклонены (пустое название), причина записана в отчёт импорта.
- **28 747 обзоров прессы** — цитаты изданий с оценками (из второго файла датасета).
- **30 142 игры допущено в рейтинг** — у остальных меньше 50 голосов, или это программа / дубль.
- **106 игр в must play** — короткий список «обязательно сыграть».

Почему два источника мнений: игроки (отзывы Steam) и пресса (оценки изданий) часто расходятся, а честный рейтинг должен учитывать обоих.

## 3. Что получилось

Готовый веб-сервис: открываешь http://localhost:8000/ui и видишь пять страниц — рейтинг, must play, «во что поиграть» (анкета), каталог с карточками игр и аналитика. То же самое доступно программам через REST API (21 эндпоинт, документация в Swagger), плюс ML-прогноз по загруженному CSV.

## 4. Как это работает: путь данных

1. **Скачать** — два CSV с Google Drive (`python -m app.etl.download_data`).
2. **Очистить** — ETL разбирает форматы и приводит к единому виду, битые строки уходят в отчёт.
3. **Сохранить** — PostgreSQL, upsert без дублей.
4. **Посчитать** — индекс, must play и похожие игры считаются заранее: сервис `scheduler` делает это по расписанию (cron из `RATING_CRON`, по умолчанию понедельник 03:00 UTC) или по кнопке.
5. **Отдать** — API читает готовые таблицы, поэтому отвечает быстро.

Почему считаем заранее: похожие игры для 30 тыс. игр строятся около 45 секунд — на каждый запрос так нельзя.

Три контейнера в docker compose: `db` (PostgreSQL), `app` (API и сайт, миграции применяются при старте), `scheduler` (плановый пересчёт).

## 5. Как унифицировали данные (задача минимум)

Сырые данные Steam собраны из разных версий API, поэтому одно и то же поле записано по-разному. Что чистили (код — `app/etl/cleaning.py`, `app/etl/reviews.py`):

| Проблема | Пример | Что сделали |
|---|---|---|
| Число владельцев — диапазон строкой в двух форматах | «0 - 20000» и «0 .. 20,000» | разбираем в два числа: min и max |
| Жанры, категории, теги в разных структурах | список строк; список словарей `{"id","description"}`; теги — словарь «тег → число голосов» | приводим к одному списку имён без дублей |
| Языки в трёх форматах | JSON-список, текст через запятую, HTML со звёздочками и `<br>`, иногда экранированный несколько раз (`&amp;lt;`) | снимаем HTML, разбиваем, сводим синонимы по словарю (например, названия языков на других языках): 3 587 «разных» значений → 103 языка |
| Оценки прессы в разных шкалах | 4/5, 8/10, 17/20, 85/100, 85% | переводим в 0–100; бессмысленные вроде 11/10 отбрасываем |
| Одно издание под разными именами | «Rock, Paper, Shotgun» и «Rock Paper Shotgun» | общий ключ: нижний регистр без пунктуации; 11 152 написания → 9 246 изданий |
| Metacritic = 0 | 0 означает «оценки нет», а не «ноль баллов» | пишем NULL, иначе средние были бы занижены |
| Строки без id или названия, дубли | — | отклоняем, причину пишем в `etl_runs` |

Как грузили: файл 925 МБ читается **потоково** (по строке, не целиком в память), пачками по 1000 и записывается через **upsert** — повторный запуск не создаёт дублей, а обновляет записи. Если импорт прервался, запуск помечается `failed`.

## 6. Структура проекта

Путь данных: Google Drive → скачивание → ETL → PostgreSQL → сервисы (рейтинг, рекомендации, ML) → API и веб-страницы.

Слои кода:
- **роутеры** (`app/api`) — принимают HTTP-запрос и проверяют параметры;
- **сервисы** (`app/services`) — бизнес-логика: формулы, правила;
- **репозитории** (`app/repositories`) — SQL-запросы;
- **модели** (`app/models`) — таблицы БД.

Зачем: формулу рейтинга можно тестировать без БД и HTTP, а SQL не размазан по коду.

Прочее на слайде: Pydantic-схемы раздельные для создания, обновления и ответа (клиент не может прислать, например, `index_score`); единый формат ошибок; фильтры, сортировка и пагинация; всё поднимается одной командой `docker compose up`. 19 таблиц, связи «многие ко многим» — игра ↔ жанры, теги, категории, языки, разработчики.

## 7. Рейтинг и бизнес-правила

**Индекс = 0,4 × пресса + 0,6 × игроки.** Игрокам вес больше: их голосов в тысячи раз больше, и они ближе к ответу «стоит ли играть». Если у игры меньше двух оценок прессы, индекс = оценка игроков (одна рецензия — не мнение прессы).

**Оценка игроков — байесовская** (подробно в словаре). Простая доля положительных не годится: 100% у 30 человек выше, чем 96% у миллиона. Байесовская оценка тянет игру с малым числом голосов к средней по каталогу, пока голосов не станет много (порог m = 20 000). Пример со слайда: 99% у тысячи фанатов не обгоняют 96% у 835 тысяч.

**Допуск в рейтинг:** от 50 голосов (меньше — шум), только игры (программы вроде Wallpaper Engine исключаются по жанрам Steam: Utilities, Video Production и т.п.), без дублей (одна игра под двумя app_id — оставляем запись с бо́льшим числом голосов).

**Флаг расхождения:** если пресса и игроки расходятся больше чем на 20 пунктов — пометка «переоценена прессой» или «недооценена». Пресса в среднем на 7 пунктов щедрее игроков (85,4 против 78,3), поэтому перед сравнением из оценки прессы вычитаем 7. В сам индекс эта поправка не идёт — она наказывала бы игры, которые хвалят все.

**Must play:** только игры с 10 000+ голосов — список должен состоять из игр, которые знают многие. Статусы: `candidate` → `in_list` → `dropped`.
- Вход: индекс ≥ 93 — игра становится кандидатом.
- Кандидат удержался ≥ 92 на следующем пересчёте — попадает в список. Два пересчёта нужны, чтобы случайный скачок не заносил игру в список.
- Порог выхода (92) ниже порога входа (93) — это **гистерезис**: игра на границе не прыгает туда-обратно при каждом пересчёте.

**Атомарный пересчёт:** весь пересчёт — одна транзакция: либо обновились все оценки, история и статусы, либо ничего. Второй пересчёт, пока идёт первый, получает 409.

## 8. Рекомендации: «если понравилась эта»

Это **контентная** рекомендательная система — похожесть по описанию игры, а не по поведению пользователей (данных о пользователях в датасете нет).

1. Каждая игра — набор «слов»: её жанры, теги, категории.
2. **TF-IDF** взвешивает слова: тег, который есть у половины каталога («Indie»), почти ничего не говорит; редкий («Farming Sim») — говорит много.
3. Похожесть двух игр — **косинусная близость** их векторов (1 — совпадают, 0 — ничего общего). Ближайших соседей ищет `NearestNeighbors`.
4. В выдаче 0,8 × похожесть + 0,2 × качество (индекс), чтобы среди одинаково похожих наверх шли хорошие игры.

Результаты считаются заранее (10 соседей на игру, 301 420 пар) и лежат в таблице, поэтому API отвечает мгновенно.

**Как проверяли.** Проверять по жанрам нельзя — модель на них построена, результат будет завышен. Поэтому для проверки модель строится только по жанрам и категориям, а «попадание» — общий **редкий тег**, которого модель не видела. Метрика **Precision@10** — доля попаданий среди 10 рекомендаций. Сравнение с базовыми линиями:
- наша модель — 0,795;
- 10 самых популярных игр — 0,587;
- 10 случайных — 0,455.

Ещё две метрики: **покрытие** 95% (столько игр каталога хоть раз попадают в чьи-то рекомендации — система не советует всем одно и то же) и **разнообразие** 0,45 (насколько непохожи игры внутри одной выдачи).

## 9. ML: прогноз для игры, у которой ещё нет отзывов

Сценарий: игра только вышла или анонсирована — отзывов нет, но есть описание. Две задачи **бинарной классификации** («да / нет»):
- **hit** — попадёт ли игра в верхние 10% по оценке игроков (по нижней границе Уилсона среди игр с 10+ голосами);
- **press** — поставит ли пресса 75 и выше.

**Признаки (115 штук)** — только то, что известно до релиза: цена, бесплатна ли, год и месяц выхода, число языков, достижения, DLC, платформы, топ-20 жанров, топ-60 тегов, топ-25 категорий (каждый — отдельный столбец 0/1, это **one-hot**). Счётчики сжаты логарифмом (`log1p`), чтобы игры с 5 000 достижений не ломали модель.

**Утечка данных.** Голоса, онлайн и число владельцев убраны: из голосов считается сам ответ, и модель «подсмотрела» бы его.

**Три алгоритма**, выбор по ROC-AUC на отложенной выборке (80% обучение / 20% тест, со **стратификацией** — доля хитов одинакова в обеих частях):
- **логистическая регрессия** — линейная, простая базовая линия;
- **случайный лес** — много деревьев решений, голосуют;
- **градиентный бустинг** — деревья строятся по очереди, каждое исправляет ошибки предыдущих.

| | LogReg | Лес | Бустинг |
|---|---|---|---|
| hit (56 763 игры) | 0,776 | 0,804 | **0,804** |
| press (5 875 игр) | 0,695 | **0,740** | 0,709 |

Лучшая модель сохраняется в `.pkl` вместе с предобработкой (пайплайн), поэтому в API можно отдать сырую строку CSV Steam. Эндпоинты: `/ml/upload-model` (загрузить модель), `/ml/predict` (прогноз по JSON), `/ml/predict-from-csv` (по файлу).

Почему press хуже: данных в 10 раз меньше, и 91% игр с оценками прессы и так получают 75+ — модели сложно найти редкие «плохие».

## Словарь

**API** — программный интерфейс: адреса (эндпоинты), на которые программа шлёт запросы и получает JSON.

**ETL** (Extract, Transform, Load) — извлечь данные из источника, преобразовать (почистить, унифицировать), загрузить в БД.

**Upsert** — «вставить или обновить»: если запись с таким ключом есть — обновляется, нет — добавляется. В PostgreSQL — `INSERT ... ON CONFLICT DO UPDATE`.

**ORM** (SQLAlchemy) — работа с таблицами как с классами Python. **Alembic** — миграции: версии схемы БД.

**Pydantic** — проверка и описание данных запроса/ответа; ошибки проверки → 422.

**Коды ответа**: 400 — неверный запрос, 404 — не найдено, 409 — конфликт (дубль или пересчёт уже идёт), 422 — данные не прошли проверку, 503 — БД недоступна.

**CI** (Continuous Integration) — автоматическая проверка кода при каждом push.

**Нижняя граница Уилсона** — консервативная оценка доли положительных отзывов: «с вероятностью 95% настоящая доля не ниже X». Чем меньше голосов, тем сильнее занижает. 3 из 3 положительных → около 44%, 9 000 из 10 000 → около 89%. Минус: при нескольких тысячах голосов штраф почти исчезает, и нишевые игры с 99% обгоняют всем известные с 96%. В проекте осталась только для определения «хита» в ML.

**Байесовская оценка** (как в IMDb Top 250) — оценка = (v × доля + m × средняя) / (v + m), где v — число голосов игры, m = 20 000, средняя — средняя доля положительных по каталогу. При 1 000 голосах игра почти целиком получает среднюю по каталогу, при миллионе — свою долю. Смысл: высокое место надо подтвердить большим числом голосов.

**Гистерезис** — разные пороги входа (93) и выхода (92), чтобы значение у границы не переключало статус туда-обратно.

**TF-IDF** (Term Frequency — Inverse Document Frequency) — вес слова: высокий, если слово есть у этой игры и редко встречается в каталоге.

**Косинусная близость** — похожесть двух векторов по углу между ними: 1 — одинаковы по направлению, 0 — не пересекаются.

**Precision@10** — доля «правильных» среди первых 10 рекомендаций.

**Базовая линия** (baseline) — простой способ, с которым сравнивают модель: если модель не лучше случайного или популярного — она бесполезна.

**Бинарная классификация** — предсказание «да / нет» (вероятность от 0 до 1).

**ROC-AUC** — качество классификатора: вероятность того, что случайный «да» модель оценит выше случайного «нет». 0,5 — угадывание, 1,0 — идеально, 0,8 — хорошо. Не зависит от выбранного порога и устойчива к дисбалансу классов (хитов всего 10%).

**Утечка данных** (data leakage) — в признаки попадает информация, из которой считается ответ; на тесте модель выглядит отлично, в жизни бесполезна.

**Стратификация** — разбиение на обучение и тест с сохранением доли классов.

**One-hot** — категория превращается в столбцы 0/1: «есть жанр RPG» — 1, нет — 0.

**log1p** — log(1 + x): сжимает большие числа, 0 остаётся 0.

**Логистическая регрессия / случайный лес / градиентный бустинг** — три классических алгоритма классификации: линейная модель; ансамбль независимых деревьев решений; ансамбль деревьев, где каждое следующее исправляет ошибки предыдущих.

**pkl** (pickle) — файл с сохранённым объектом Python, здесь — обученной моделью вместе с предобработкой.

**Пайплайн** (Pipeline) — цепочка «предобработка → модель» в одном объекте: одинаковые преобразования при обучении и при прогнозе.

**Атомарность / транзакция** — набор изменений, который применяется целиком или не применяется вовсе.

**Allure** — генератор отчётов о тестах. **Покрытие (coverage)** — доля строк кода, выполненных тестами.
