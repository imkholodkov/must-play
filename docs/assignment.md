	**Итоговое задание по дисциплине «Разработка на Python и инженерия данных»**

**Дисциплина:** Разработка на Python и инженерия данных  
**Тема:** Разработка информационной системы с REST API на Python и FastAPI в выбранной предметной области

*Предметная область проекта определяется студентом самостоятельно и предварительно согласовывается с преподавателем.* 

**1\. Цель проекта**  
В рамках итогового проекта необходимо спроектировать и разработать полноценную информационную систему с REST API на Python.  
Проект должен продемонстрировать умение студента применять на практике знания, полученные в рамках курса: 

- разработка приложений на Python;   
- разработка REST API;  
- работа с FastAPI;  
- проектирование реляционных баз данных;  
- работа с ORM;  
- проектирование структуры данных и ERD;  
- реализация бизнес-логики;  
- тестирование программного обеспечения;  
- использование Git и GitHub;  
- проведение code review;  
- настройка CI;  
- документирование проекта;  
- разработка простого клиентского интерфейса.

Итоговый проект должен представлять собой не просто набор CRUD-операций, а законченную небольшую информационную систему с понятной предметной областью и бизнес-логикой. 

**2\. Предметная область**   
Предметную область студент выбирает самостоятельно. Выбранная предметная область должна быть предварительно согласована с преподавателем.

Предметная область должна позволять построить систему с несколькими связанными сущностями и реализовать бизнес-логику.   
Примеры возможных направлений (студент может предложить собственную предметную область):

* интернет-магазин;  
* библиотека;  
* система бронирования;  
* кинотеатр.

*Проект, состоящий из одной сущности и простого CRUD без дополнительных связей и бизнес-логики, не соответствует требованиям итогового задания.* 

**3\. Требования к Backend**  
Предусмотрены следующие обязательные требования:

* Backend должен быть разработан на **Python** с использованием **FastAPI**.   
* Допускается использование дополнительных библиотек и инструментов, необходимых для реализации проекта. 

*Рекомендуемый стек:*

* Python 3.11+;  
* FastAPI;  
* Pydantic;  
* SQLAlchemy;  
* PostgreSQL;  
* Alembic;  
* pytest.

*Допускается использование других технологий по согласованию с преподавателем.* 

**4\. Требования к базе данных**   
В проекте должна использоваться реляционная база данных. Необходимо самостоятельно спроектировать структуру базы данных в соответствии с выбранной предметной областью.

Минимальные требования: 

* не менее **4-5 связанных таблиц**;  
* наличие связей один-ко-многим и многие-ко-многим (через ассоциативную таблицу);  
* первичные и внешние ключи, ограничения целостности (NOT NULL, UNIQUE, CHECK);  
* индексы для полей, по которым выполняются поиск и фильтрация;  
* схема создаётся и изменяется только через миграции Alembic, миграции обратимы (downgrade);  
* команда или скрипт наполнения БД тестовыми данными (seed);  
* ERD-диаграмма в репозитории (dbdiagram.io, draw.io, Mermaid).

**5\. Требования к бизнес-логике**  
Система должна содержать **не менее 3 бизнес-правил**, выходящих за рамки CRUD, например:

* проверка ограничений (нельзя забронировать занятое место, нельзя выдать книгу при отсутствии экземпляров);  
* изменение состояния сущностей (статусы заказа);  
* расчёты (итоговая стоимость с учётом скидок, штрафы за просрочку);  
* транзакционные операции (оформление заказа списывает остатки и создаёт позиции атомарно);  
* агрегирующие отчёты (выручка по периодам, топ-N популярных объектов).


*Бизнес-логика выносится в отдельный слой (services), а не пишется в обработчиках эндпоинтов.*

**6\. Требования к REST API**

* не менее 8-10 эндпоинтов: CRUD для основных сущностей и специальные операции бизнес-логики;  
* корректные HTTP-методы и статус-коды (200, 201, 204, 400, 404, 409, 422);  
* валидация через Pydantic, раздельные схемы для создания, обновления и ответа;  
* пагинация, фильтрация и сортировка минимум в одном списочном эндпоинте;  
* единый формат ошибок и централизованная обработка исключений;  
* автодокументация Swagger/OpenAPI с описаниями и примерами;  
* использование Depends для сессии БД и общих зависимостей.

**7\. Инженерия данных (ETL и аналитика)**  
Проект должен включать блок работы с данными:

* ETL-скрипт импорта данных из CSV-файла или внешнего API (например, справочник, каталог, исторические данные) в БД;  
* этапы: извлечение, валидация и очистка (пропуски, дубликаты, некорректные форматы), преобразование, загрузка;  
* идемпотентность: повторный запуск не создаёт дубликатов;  
* логирование результата запуска (сколько строк загружено, сколько отклонено и почему);  
* запуск скрипта из командной строки (например, python \-m app.etl.import\_data \--source data/items.csv);  
* не менее 2 аналитических эндпоинтов с агрегациями (группировка, суммы, средние, топ-N, динамика по периодам);  
* по желанию: плановый запуск (cron, APScheduler).

**8\. Требования к архитектуре кода**  
Рекомендуемая структура:  
project/  
├── app/  
│   ├── api/          \# роутеры  
│   ├── models/       \# SQLAlchemy-модели  
│   ├── schemas/      \# Pydantic-схемы  
│   ├── services/     \# бизнес-логика  
│   ├── repositories/ \# доступ к данным БД (опционально)  
│   ├── etl/          \# скрипты импорта и обработки данных  
│   ├── core/         \# конфигурация, безопасность  
│   └── main.py  
├── migrations/  
├── tests/  
├── docs/  
├── docker-compose.yml  
├── requirements.txt  
└── [README.md](http://README.md)  
*Настройки и секреты хранятся в переменных окружения (.env), а не в коде. В репозитории должен быть файл .env.example.*

**9\. Требования к тестированию**

* тесты на pytest, использование TestClient FastAPI;  
* отдельная тестовая БД или откат транзакций между тестами;  
* unit-тесты сервисного слоя и ETL-функций очистки данных (минимум 1);  
* интеграционные тесты API (минимум 2, включая негативные сценарии);  
* покрытие кода не менее 70% (pytest-cov).

**10\. Требования к клиентскому интерфейсу**  
Простой интерфейс, работающий через ваш API. Допустимые варианты:

* веб\-страницы на HTML/JS (fetch) или шаблонах Jinja2;  
* React/Vue (по желанию).

*Минимум: просмотр списка объектов, создание и редактирование, выполнение одной ключевой бизнес-операции, отображение ошибок пользователю.*

**11\. Требования к процессу разработки (Git, code review, CI)**  
*Git и GitHub*

* репозиторий на GitHub, осмысленная история (не менее 15-20 коммитов) с понятными сообщениями (например, feat:, fix:, test:);  
* ветка main защищена от прямых push, разработка ведётся в feature-ветках;  
* все изменения попадают в main только через Pull Request; минимум 3 PR с описанием (что сделано, зачем, как проверить);  
* .gitignore, отсутствие секретов в репозитории.

*Code review (обязательно, между студентами группы)*

* каждому студенту назначается ревьюер из числа одногруппников;  
* ревьюер добавляется в репозиторий автора как collaborator (или работает через fork);  
* студент обязан провести ревью минимум 2 PR коллеги и получить ревью минимум на 2 своих PR;  
* ревью выполняется средствами GitHub: комментарии к строкам кода и итоговое решение (Approve / Request changes / Comment);  
* в ревью должно быть не менее 3 содержательных замечаний на PR (архитектура, читаемость, обработка ошибок, тесты, безопасность, нейминг); формальные «LGTM» без комментариев не засчитываются;  
* автор отвечает на замечания: исправляет код отдельными коммитами или аргументированно возражает в треде;  
* PR сливается в main только после Approve и зелёного CI;  
* ссылки на PR с ревью прикладываются к отчёту и показываются на защите.

*CI на GitHub Actions*

* workflow запускается при каждом push и PR;  
* шаги: установка зависимостей, линтинг (ruff или flake8), запуск pytest с отчётом о покрытии (порог не ниже 70%);  
* статус CI виден в PR; слияние при красном CI запрещено (branch protection).
